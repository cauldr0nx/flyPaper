# M1 — ingest spike

**Gate: a 10,000-request run parses with zero fatal errors and a documented field schema.
Met.** 9,998 records, 0 malformed, 0 fatal, both live and from a file.

Nothing in this report is copied from documentation. Every claim below was read off the
installed binary's actual output.

## 1. What was run

| | |
|---|---|
| Fuzzer | `ffuf version: 2.1.0-dev` (`~/go/bin/ffuf`) |
| Target | ffufme, built locally from `BuildHackSecure/ffufme` at commit `8814611cca35e824ea70f257684604c2c422258a` |
| Image | `ffufme:8814611`, id `94d864f9f5da`, built 2026-09-11 |
| Binding | `127.0.0.1:8099` only. Nothing left the loopback interface. |
| Wordlist | 10,000 entries, generated by `bench/make_wordlist.py --seed 20260911`, sha256 `f4f075a079a5f6a4268567a0248c7645e55e83c61ed5219d1ea39e2119b4a999` |

The wordlist is generated rather than downloaded — there is no SecLists checkout on this
machine — and deliberately includes a slice of entries hostile to a JSON parser: embedded
quotes, backslashes, `%`, `&`, `#`, `?`, non-ASCII (`café`, `日本語`), an emoji, and a
literal tab.

```bash
python bench/make_wordlist.py --out list.txt --count 10000 --seed 20260911
ffuf -mc all -json -u http://127.0.0.1:8099/FUZZ -w list.txt -noninteractive -t 40
ffuf -mc all -of json -o batch.json -u http://127.0.0.1:8099/FUZZ -w list.txt -noninteractive
```

## 2. Does `-json` stream? Yes.

This was the open question, and the answer decides the architecture. The first attempt was
useless as evidence — 10,000 requests against loopback completed in 1.2 s at 8,333 req/s,
faster than the sampler could observe. Re-run at `-rate 200` through a `| cat` pipe,
sampling the downstream file every 5 s:

```

t= 5007 ms  lines=   999  bytes=   309813
t=10014 ms  lines=  2000  bytes=   625665
t=15020 ms  lines=  3001  bytes=   940910
t=20027 ms  lines=  4003  bytes=  1256504
t=25034 ms  lines=  5004  bytes=  1571555
t=30040 ms  lines=  6006  bytes=  1887390
t=35046 ms  lines=  7007  bytes=  2202882
t=40054 ms  lines=  8008  bytes=  2518617
t=45061 ms  lines=  9010  bytes=  2834408

t=55075 ms  lines=  9998  bytes=  3145735   <- after exit
```

200 records per second, tracking `-rate 200` exactly, arriving through a pipe with no
buffering and nothing held back until exit.

**Strategy 1 (stdin NDJSON) is the live path.** `iter_tail` is implemented anyway as the
documented fallback for a producer that does not stream, and batch mode is always supported
because it is what makes offline replay benchmarking possible.

Mechanically this matches the source: `Stdoutput.Result()` calls `PrintResult` per response,
and `resultJson` writes one line with `fmt.Println` to an unbuffered `os.Stdout`.

## 3. Is stdout clean? Yes — everything else goes to stderr.

The brief noted ffuf's changelog claim that JSON mode takes precedence over quiet mode. On
this build the mechanism is simpler and stronger than that: the ASCII banner, the
configuration block and the `:: Progress: [n/10000] ... ::` counter **all go to stderr**,
so stdout carries nothing but NDJSON records. 1 MB of progress output on stderr during the
10 k run; not one byte of it on stdout.

Consequence: `ffuf ... -json | fly ingest` needs no pre-filtering, and a consumer that
merges stderr into stdout will corrupt its own input.

## 4. The field schema, as emitted

Identical field names in both modes. Key order differs between them (`duration` precedes
`scraper` on stdout, follows it in a file); nothing should depend on order.

| Field | JSON type | Notes |
|---|---|---|
| `input` | object | keyword → word. **Encoding differs by mode — see §5.** Always contains `FFUFHASH` plus the wordlist keywords. |
| `position` | integer | 1-based index into the input. |
| `status` | integer | HTTP status. |
| `length` | integer | response body bytes. |
| `words` | integer | |
| `lines` | integer | |
| `content-type` | string | hyphenated, not `content_type`. |
| `redirectlocation` | string | one word, empty when absent. |
| `url` | string | |
| `duration` | integer | **nanoseconds.** Go marshals `time.Duration` as an integer count of ns. `1405988` is 1.4 ms, not 1.4 s and not 23 minutes. |
| `scraper` | object | keyword → array of strings. `{}` when no scrapers matched. |
| `resultfile` | string | populated only under `-od`. |
| `host` | string | includes the port. |

A record as emitted on stdout:

```json

```

## 5. The one that would have quietly ruined everything

**`input` is base64 on stdout and plain text in a file.** Same ffuf, same run, same field:

| Mode | `input` as emitted | Decodes to |
|---|---|---|
| `-json` (stdout) | `{"FFUFHASH":"NjE5MWUyNQ==","FUZZ":"b2xk"}` | `6191e25`, `old` |
| `-of json` (file) | `{"FFUFHASH":"187066","FUZZ":"logout"}` | already plain |

The cause is in ffuf's source rather than its documentation: the stdout path marshals
`pkg/ffuf.Result`, whose `Input` is `map[string][]byte`, and Go base64-encodes `[]byte`;
the file path marshals `pkg/output.JsonResult`, whose `Input` is `map[string]string`.

The obvious way to paper over this is to sniff each value — *does it decode as base64 and
round-trip?* **That is wrong, and measurably so.** Of the 9,998 words in this run, **524
(5.2%) are plain text that passes exactly that test**, among them `test`, `soap`, `temp`,
`register`, `settings`, `database`, `logs` and `dump`. Sniffing would have silently
replaced one word in twenty with binary garbage, in the component whose entire job is not
to do that.

`FFUFHASH` is no help as a discriminator either: it is lowercase hex of variable length,
6–9 characters over this run, and the 3,839 records where it is 8 characters long are
themselves valid base64.

So the parser decides **per source, not per value**: `BASE64` for a stream, `PLAIN` for a
results document, an explicit `--input-encoding` override, and an `AUTO` mode that samples
64 records and is one-sided on purpose — a single value that fails to decode proves the
stream is plain, while no finite sample can prove the converse. Pinned by
`tests/test_ingest.py::test_batch_and_stream_agree_on_a_word_that_is_valid_base64`.

## 6. A request that errors produces no record at all

10,000 words in, 9,998 records out. The two missing entries are the ones containing a
literal tab (`tab\tinside` and `dir/tab\tinside`): Go rejects a control character in a URL,
so the request never goes out. ffuf counts them — the final stderr line reads
`:: Progress: [10000/10000] ... :: Errors: 2 ::` — but **under `-json` it prints no error
record and no error detail**, only that counter.

So the record count is not the request count, and the difference is visible only on stderr.
Anything downstream that computes a rate or a coverage figure from record count alone will
be quietly wrong. Worth remembering at M4.

## 7. Parser behaviour

`flypaper/ingest/ffuf.py` normalises; it does not filter, threshold or score.

- Malformed lines are counted and skipped, never fatal. A fuzzing run is long and
  expensive; losing one because a pipe was killed mid-record would be the wrong trade.
- Unknown fields are retained in `FfufResult.extra` and warned about **once** per distinct
  field — a 10,000-record stream must not emit 10,000 warnings.
- Missing fields take documented defaults; wrong types are coerced where a coercion is
  unambiguous (`"12"` → `12`) and counted in `ParseStats.coercion_failures` otherwise.
- `iter_tail` holds back a trailing partial line, because the writer may be mid-record.

Verified end to end on the full capture:

```
$ ffuf -mc all -json -u http://127.0.0.1:8099/FUZZ -w list.txt 2>/dev/null | fly ingest --quiet
flypaper: 9998 records | 0 malformed
```

Every hostile word survives the round trip intact — `quote"inside`, `back\slash`,
`both"and\slash`, `café`, `日本語`, `emoji🐛`, `dir/brace{}`, `percent%20encoded` — as do all
eight of the base64-lookalike words spot-checked from the 524.

## 8. One more thing worth having

Every record carries `FFUFHASH` whether or not the URL uses the keyword. That is ffuf's
per-request handle, and it is the thing that would let a delayed out-of-band callback be
tied back to the exact request that caused it — the dopaminergic credit-assignment idea in
§5 of the brief. It is free in the stream we are already reading, and
`FfufResult.ffufhash` exposes it. A test asserts it is present on every real record, so if
that ever stops being true the M7 work finds out immediately rather than at the end.

## 9. Corpus note

The status distribution over this run was `{404: 9997, 200: 1}` — ffufme returns a real 404
for unknown paths at the document root, so this particular run is not a wildcard host. The
soft-404 lesson lives at `/cd/no404`, and building the labelled corpus around it and the
other lesson endpoints is M2, not this milestone.
